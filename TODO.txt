TODO - SteelHacks2026-Squoders
==============================

Goal: email arrives at an internet-connected computer, gets stripped/shortened,
is sent over a Meshtastic LoRa mesh, and is displayed in a phone app.

Flow:  Gmail -> Gateway computer -> Gateway node -> LoRa mesh (private channel)
       -> End node -> (BLE) -> Endpoint phone app

Status: the gateway side works end to end on real hardware. Gmail polling,
parsing, compression into packets, LoRa transfer between two T-Beam S3 Core
nodes, and decoding on the far node were all tested (over USB, nodes side by
side). Still missing: the gateway loop that joins Gmail to the radio, and the
phone app. The project is NOT a firmware fork; both nodes run stock firmware
(2.7.10) and we use the official `meshtastic` Python library.

Legend: [ ] not started   [~] partly done   [x] done
Priority: P0 = needed for a working demo, P1 = should have, P2 = nice to have

How the pieces fit (files):
  MessagePing.py       Gmail polling + fetching full messages        (Josiah)
  MessageTransform.py  Gmail JSON -> {id, date, sender, subject, body} (Josiah)
  MessagePayload.py    byte-safe text helpers (truncate_bytes etc.)   (Josiah)
  MeshCodec.py         email dict -> compressed binary packets, and back; the
                       packet format spec lives in its docstring
  provision.py         creates the private channel on both nodes
  RadioTestSend.py / RadioTestListen.py   hardware test of the whole chain

3. PACKET FORMAT AND DELIVERY (MeshCodec.py: the gateway <-> endpoint contract)
-------------------------------------------------------------------------------
Format summary: 1 flag byte + (raw or deflated record: 4-byte UTC minutes,
sender, subject, body separated by newlines), split into packets of at most 200
bytes, each with a 3-byte header (2-byte email id, part/total in one byte, up to
3 packets per email). Full spec is the MeshCodec.py docstring.
[x] P0  Envelope, chunking on byte boundaries, reassembly of out-of-order
        packets, missing-packet detection (reassemble returns None).
[ ] P0  Reassembly timeout at the endpoint: show partial mail marked
        "incomplete" rather than waiting forever.
[~] P1  Reliability: the sender requests acks (wantAck=True) but nothing checks
        whether they arrive. Handle NAK/timeout and decide on a retry limit.
[ ] P1  Deduplicate on email id so a retried packet does not show twice. Note the
        id is only 16 bits (crc32 of the Gmail id), so ids can collide.
[ ] P1  Rate limiting: the tests sleep 5 s between packets. Replace that with a
        real queue between the codec and the radio.
[~] P2  Versioning: the upper 7 bits of the flag byte are reserved for it.
[ ] P2  Put the packet spec in docs/ for the app developers. Right now the
        MeshCodec.py docstring is the only copy.

7. SECURITY AND PRIVACY
-----------------------
[x] P0  Private channel with a random key instead of the default one. The default
        key is public: any Meshtastic user in range could read it.
[x] P0  Secrets (channel.url, channel.backup.url, secrets.json, tokens/) are in
        .gitignore. Check `git status` before every commit anyway.
[ ] P1  One shared channel means every holder of the key can read every message.
        Fine for one person's inbox; not for several users on one mesh. Options:
        Meshtastic's built-in direct-message encryption (the nodes report
        hasPKC; adds a few bytes per packet, needs both nodes to know each
        other's public keys) or our own per-user encryption inside MeshCodec
        (roughly 20-30 extra bytes per email). Neither has been tried.
[ ] P1  Only forward mail from an allowlist (see section 1).
[ ] P1  channel.backup.url holds the OLD keys, including the WaronChat channel
        that was on node 2 before provisioning. Keep it private, or delete it
        once nobody needs to restore that channel.
[ ] P2  Node 1's private key (the device's own identity key) appeared in
        terminal output that was pasted into a chat. Regenerate it if that
        transcript is ever shared.
[ ] P2  Consider redacting patterns like verification codes or account numbers.
[ ] P2  Regulatory: LoRa runs in unlicensed ISM bands (915 MHz in the US) with
        power limits set by the region. Keep the region correct for where the
        demo happens.
