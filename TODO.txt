==============================

Goal: email arrives at an internet-connected computer, gets stripped/shortened,
is sent over a Meshtastic LoRa mesh, and is displayed in a phone app.

Flow:  Email -> Gateway computer -> (BLE) -> Gateway node -> LoRa mesh
       -> End node -> (BLE) -> Endpoint phone app

Status today: MessagePing.py is a stub (empty function bodies, does not parse),
MessageTransform.py is empty, no app exists. Nothing runs yet. The project is
NOT a firmware fork; both nodes run stock Meshtastic firmware.

Priority: P0 = needed for a working demo, P1 = should have, P2 = nice to have

2. STRIPPING AND SHORTENING (MessageTransform.py, currently empty)
------------------------------------------------------------------
Meshtastic text payloads are small (roughly 200-230 bytes per packet), and LoRa
airtime is slow and duty-cycle limited. This is the core of the project, so the
transform needs to be aggressive and deterministic.
[ ] P0  Parse MIME: prefer text/plain; if only text/html, convert to text
        (e.g. BeautifulSoup or html2text). Ignore attachments and inline images
        (optionally note "2 attachments").
[ ] P0  Strip: quoted replies ("> ..." and "On <date>, X wrote:" blocks),
        signatures ("-- " delimiter, "Sent from my iPhone"), legal/unsubscribe
        footers, tracking links, excess whitespace and blank lines.
[ ] P0  Extract only the fields we send: sender (name or short address),
        subject, and the shortened body. Decode RFC 2047 headers and non-UTF-8
        charsets properly.
[ ] P0  Shorten to a byte budget, not a character budget. Count UTF-8 bytes;
        emoji and non-Latin text use 2-4 bytes each.
[ ] P1  Shortening strategies, roughly in order of effort:
          1. Truncate with an ellipsis marker.
          2. URL shortening or removal (replace with "[link]").
          3. Abbreviation/dictionary substitution.
          4. Compression (zlib/brotli/smaz-style) of the body; check that it
             actually wins at ~200 bytes since headers add overhead.
          5. LLM summarization of the body (optional; needs an API key and
             network on the gateway, and must be deterministic enough to demo).
[ ] P1  Make the output configurable: max bytes per message, max chunks per
        email, and whether to send subject-only when the body is long.
[ ] P1  Unit tests with real-world samples: newsletters, HTML-only mail,
        forwarded chains, non-English mail, empty body. Keep fixtures in a
        tests/ folder.


3. MESSAGE FORMAT AND CHUNKING (shared gateway <-> endpoint contract)
---------------------------------------------------------------------
[ ] P0  Define the envelope, for example:
          <ver>|<email-id>|<part>/<total>|<from>|<subject>|<body...>
        Keep header overhead tiny. Only the first chunk needs from/subject.
[ ] P0  Chunking: split on UTF-8 boundaries (never mid-codepoint) so each chunk
        fits one packet. Include sequence numbers so the endpoint can
        reassemble out-of-order or partial deliveries.
[ ] P0  Reassembly at the endpoint with a timeout: show partial mail marked
        "incomplete" rather than waiting forever.
[ ] P1  Reliability: Meshtastic has want_ack and routing-level retries for
        direct messages, but broadcast is unreliable. Send to a specific node
        ID with acks enabled and handle NAK/timeout. Decide on retry limit.
[ ] P1  Deduplicate on email-id so a retried chunk does not show twice.
[ ] P1  Rate limiting: space chunks out so we do not flood the mesh or hit the
        radio's duty-cycle limits. Add a queue between the transform and the
        radio.
[ ] P2  Version byte in the envelope so the format can evolve without breaking
        older apps.
